# Автоматичні оновлення Movie Discovery на сервері

Зміни в `main` публічного репозиторію запускають збірку API, web і бота на GitHub-hosted runner. Приватний workflow викликає встановлений оновлювач кожні 15 хвилин. Оновлювач від імені root перевіряє поточний `main`, знаходить успішний запуск `build-server-release.yml` для цього SHA, завантажує його артефакт, перевіряє SHA-256 і бере з нього digest кожного образу. Перед зупинкою сервісів та перед публікацією він ще раз звіряє поточний `main`. Запуск за розкладом GitHub може затримуватися. Workflow також можна запустити через Actions → Deploy Movie Discovery → Run workflow.

## 1. Створіть приватний репозиторій керування

1. Створіть приватний репозиторій під своїм GitHub-обліковим записом із гілкою `main`. Доступ на запис до обох `main` має надаватися лише людям, яким ви довіряєте запуск релізу. Забороніть створення форків приватного репозиторію, якщо налаштування акаунта це дозволяють.
2. Скопіюйте `deploy.yml` у `.github/workflows/deploy.yml` приватного репозиторію. Серверний runner реєструється лише в цьому приватному репозиторії.
3. Створіть fine-grained GitHub token для публічного репозиторію Movie Discovery з дозволом Actions → Read-only. Збережіть його у файлі `/etc/movie-discovery/github-actions-token`, доступному лише root. Розміщення токена на сервері дає змогу перевіряти походження артефакту всередині привілейованого оновлювача. Поновлюйте токен до завершення строку дії.
4. У GitHub Packages відкрийте доступ Public для `movie-discovery-api`, `movie-discovery-web` і `movie-discovery-bot` після першої збірки. Це дає серверу доступ до опублікованих образів без registry credential. У Packages лишіть право публікації тільки для довіреного workflow.
5. Після відновлення та приймання початкового сервера встановіть Actions variable `MOVIE_DISCOVERY_AUTO_DEPLOY` у `true`. Видалення змінної або значення `false` зупиняє нові перевірки, вже запущений деплой завершується окремо.

[Безпечне використання GitHub Actions](https://docs.github.com/en/actions/reference/security/secure-use) · [Права для завантаження артефактів](https://docs.github.com/en/rest/actions/artifacts#download-an-artifact)

## 2. Розмістіть дані та конфігурацію

Початкове перенесення PostgreSQL, MinIO і ключів DataProtection описане в `../SERVER_TRANSFER_UK.md`. Для Funnel використовуйте `../TAILSCALE_VPS_UK.md`. Спочатку відновіть і перевірте базовий стек, оскільки оновлювач приймає лише вже робочий проєкт `moviediscovery`. Для автоматизації потрібні Linux amd64, Python 3.10+, Git, `sudo`, `findmnt` і Docker Compose із підтримкою наявних `!reset` та `!override`.

Після `scripts/server-preflight.sh` виберіть реальні точки монтування на великих дисках. Переконайтеся, що вони налаштовані в `/etc/fstab` чи відповідних systemd mount units. `mounts` у `update.json` має містити точки монтування, які повертає `findmnt -n -o TARGET -T <шлях>`. Випадкове повернення до `/` після зникнення диска зупиняє оновлення. Урахуйте обсяг даних Docker, шлях containerd для image store Docker 29, робочі файли runner, кеш IMDb та місце для копії БД і WAL. Якщо Docker наразі використовує системний диск, запишіть фактичне значення і підберіть запас. Перенесення загального Docker або containerd на інший диск плануйте окремо, оскільки воно зачіпає всі проєкти хоста.

Для VPS з одним диском задайте `"allow_root_storage": true` та `"/"` для всіх значень у `mounts`. Виберіть наявні шляхи для `state_dir` та `backup_dir` і фактичний шлях containerd, за типової конфігурації `/var/lib/containerd`. Якщо використовується лише один розділ, оновлювач бере найбільший налаштований запас для цього розділу. Перед schema-релізом додає до нього обсяг БД для архіву і подвійний обсяг для копії й WAL. Зберігайте додаткову копію поза VPS на випадок відмови диска.

На сервері встановіть перевірені файли з Git у каталоги адміністратора. Створіть `state_dir` і `backup_dir` на вибраних дисках із правами `0700` для root. Власником усіх батьківських каталогів цих шляхів і файлів оновлювача має бути root. Батьківські каталоги мають бути справжніми каталогами без символічних посилань і без права запису для групи чи інших користувачів. Наприклад, залиште `/srv/app-storage` під керуванням root (режим `0755`), а для `md-release` виділіть окремий сусідній каталог `/srv/app-storage/runner`. В `update.json` вкажіть ті самі bind mounts і середовище, які використовує вже запущений продакшн-стек. `BACKUP_DIR` у приватному Compose env може вказувати на каталог для інших резервних копій. `backup_dir` в `update.json` призначений для копій автоматичних релізів.

```bash
sudo install -d -m 0700 /etc/movie-discovery/compose/minio
sudo install -d -m 0755 /usr/local/lib/movie-discovery
sudo install -m 0644 docker-compose.yml docker-compose.server.yml docker-compose.funnel.yml /etc/movie-discovery/compose/
sudo install -m 0644 minio/Dockerfile /etc/movie-discovery/compose/minio/Dockerfile
sudo install -m 0600 deploy/runner/update.example.json /etc/movie-discovery/update.json
sudo install -m 0644 deploy/runner/resolve-release.py /usr/local/lib/movie-discovery/resolve-release.py
sudo install -m 0755 deploy/runner/movie-discovery-update.py /usr/local/sbin/movie-discovery-update
sudo install -m 0600 /dev/null /etc/movie-discovery/github-actions-token
sudoedit /etc/movie-discovery/github-actions-token
sudoedit /etc/movie-discovery/update.json
```

Робоча конфігурація `/etc/movie-discovery/production.env` має належати root і мати права `0600`. Під час встановлення адаптуйте шляхи та порти у цьому файлі. Створіть `CATALOG_CACHE_DIR` на диску для даних. API використовує його для стиснених IMDb-файлів, які можна завантажити повторно. За замовчуванням IMDb та TMDb перевіряються раз на 24 години, а TMDb переглядає п'ять сторінок популярних тайтлів та Discover. Додатковий Brave Search вимкнений за замовчуванням. Для його ввімкнення потрібен ключ і тариф із правом зберігати отримані URL. Оновлювач перевіряє відбиток інстальованих Compose-файлів і Dockerfile MinIO. Для змін мережі, storage, PostgreSQL, MinIO або способу зовнішньої публікації спочатку перевірте й застосуйте серверний конфіг окремо, а потім установіть файли з Linux checkout у каталозі `compose`, щоб їх байти збігалися з GitHub-збіркою.

## 3. Зареєструйте runner з вузьким доступом

Використайте окремого системного користувача, наприклад `md-release`. Встановіть runner для Linux x64 на диск для застосунків за командою з Settings → Actions → Runners → New self-hosted runner приватного репозиторію. Укажіть label `movie-discovery-production`. Встановіть systemd-сервіс для `md-release` за настановою GitHub. Перевірте, що користувач не входить до групи Docker та інших адміністративних груп і не має доступу на запис до системного Python, Git, Docker CLI, скриптів оновлювача, Compose-файлів або конфігурації. Розгортання використовує один точний дозвіл `sudo`, який перевіряється через `visudo -f /etc/sudoers.d/movie-discovery-update`.

```sudoers
md-release ALL=(root) NOPASSWD: /usr/local/sbin/movie-discovery-update --deploy
```

Робоча папка runner доступна лише `md-release`. Додайте залежність systemd `RequiresMountsFor=` для її фактичного шляху, якщо вона на окремому диску. Після першого успішного запуску звірте SHA в Actions, `active.json` і `docker inspect`. Перевірте каталог, постери, авторизацію та Telegram polling ззовні.

[Реєстрація self-hosted runner](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/add-runners) · [Запуск runner як сервісу](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/configure-the-application)

## 4. Міграції та відновлення

Завантаження образів відбувається до планового простою. Під час оновлення `bot`, `web` і `api` зупиняються. За наявності нових EF-міграцій оновлювач забороняє нові з’єднання з робочою БД через `ALLOW_CONNECTIONS false` та перевіряє, чи залишилися активні з’єднання або підготовлені транзакції. Якщо вони залишилися, оновлення переривається і робоча БД знову приймає з’єднання. Заплануйте зупинку інших клієнтів перед таким релізом. Оновлювач створює копію робочої БД через `CREATE DATABASE … TEMPLATE`. Цей режим підтримує звичайну БД із типовими ACL, tablespace та налаштуваннями ролей. Реліз також створює архів PostgreSQL і SQL глобальних ролей, перевіряє таблицю вмісту й зберігає контрольні суми. За schema-релізу джерелом архіву є кандидатна копія до міграцій.

Кандидатні API та web стартують під окремими іменами без опублікованих портів. `MovieDiscovery__DeploymentProbe=true` вимикає фонові імпорти і seed. Оновлювач перевіряє `/api/health/ready` через кандидатний web та точний список EF-міграцій. Нові міграції застосовуються до кандидатної копії. Під час публікації оновлювач переносить початкову БД під резервне ім’я та надає кандидату робоче ім’я й можливість приймати з’єднання в одній транзакції. Помилка до публікації повертає попередні образи і доступ до початкової БД. Після публікації оновлювач зберігає робочу БД з усіма новими записами, навіть якщо запуск образів не пройшов. За незмінної схеми перевірка працює на чинній БД без заміни. Бот запускається лише якщо він працював до оновлення.

У `state_dir` є `active.json` для активного релізу, `pending.json` для перерваного процесу і `failed.json` для помилки. Перед ручними діями вимкніть `MOVIE_DISCOVERY_AUTO_DEPLOY`, дочекайтеся завершення workflow, збережіть ці файли окремо й перевірте фактичні контейнери, журнал API та імена БД. Ключ `phase` вказує на етап.

- `freeze` або `probe` означає, що робоче ім’я БД лишилося за початковою БД. Якщо є `candidate_database`, під’єднайтеся до БД `postgres`, звірте OID робочої БД з `original_oid` і відновіть доступ командою `ALTER DATABASE <робоче_ім’я> ALLOW_CONNECTIONS true`. Перевірте точні імена контейнерів у `probe_api` та `probe_web` і зупиніть їх, якщо процес перервався до їх видалення. Поверніть попередні контейнери через Compose з override із поля `rollback` і перевірте readiness.
- `publish` означає, що перемикання могло відбутися. Звірте OID робочої БД з `original_oid` і `candidate_oid`. Якщо перемикання відбулося, збережіть поточний стан і виправте новий реліз або поверніть сумісні з поточною схемою образи. Стару копію під іменем `previous_database` використовуйте для відновлення лише після оцінки нових записів. Якщо робоча БД зберегла початковий OID, дотримуйтеся кроків для `freeze`.

Винесіть `pending.json` з `state_dir`, коли ви перевірили робочу версію і зберегли журнал. Щоб повторити той самий SHA після усунення причини, так само архівуйте `failed.json`. Для ручного перезапуску після успішного релізу додавайте `-f` зі шляху `override` в `active.json` до базового `docker compose --env-file ... -f docker-compose.funnel.yml`. Інакше Compose використає початкові теги з приватного env.

Після успішного запуску оновлювач прибирає застарілі посилання на образи, які він записав сам. Він зберігає поточні й попередні образи, одну копію PostgreSQL за `keep_database_copies` і три останні зареєстровані архіви за `keep_release_archives`. Архів, потрібний збереженій копії PostgreSQL, залишається на диску додатково. Для видалення старішої БД потрібен точний збіг імені та OID, а також чинна SHA-256 перевірка архіву. Плануйте зовнішнє резервне копіювання PostgreSQL, MinIO та ключів окремо від локальних архівів релізу. `reserve_gib` зупиняє наступний реліз, якщо вільного місця бракує.
