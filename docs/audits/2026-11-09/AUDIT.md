# MovieDiscovery: аудит працездатності 09.11.2026

## Висновок

Проєкт частково працездатний. Живий каталог, пошук, картка та окрема сторінка схожості працюють; публічну готовність не підтверджено. Блокери: доступ гостя до приватних списків, несумісний payload онбордингу, зламана схожість на головній та міграція гостьових даних. Код у межах аудиту не виправлявся.

База аналізу: HEAD `196b62d096077fab8691d3d19f881d19d86ccdd3`, початково чистий Git; TZ.md і PLAN.md. Два незалежні read-only аналізи виконано моделлю `gpt-6-luna` (backend/bot та frontend/e2e). Оркестратор перевірив ключові знахідки в коді та виконав живий HTTP/browser smoke.

## Середовище та його зміна

Спочатку Docker Engine був недоступний, порти 3001/5200/5433 не слухали. Пізніше Docker став доступним і з'явилися moviediscovery-db/api/web/bot/tunnel. Аудит ці контейнери не запускав, не перезапускав і не модифікував: власник запуску не встановлений, тому вони захищені від cleanup.

Для локального огляду оркестратор запустив frontend на 127.0.0.1:3101. Початковий dev наклався на агентський build у спільній .next і спричинив ENOENT/MODULE_NOT_FOUND. Це помилка організації аудиту, а не підтверджений дефект застосунку. Dev зупинено, сервер наступного невдалого перегляду також зупинено, після чого виконано успішну послідовну production-збірку. Остаточна перевірка проведена на живому Docker web :3001. Поточний локальний допоміжний сервер :3101 підлягає фінальному cleanup.

## Знахідки та уточнення агентських висновків

1. P0: анонімний шлях у ListsController не перевіряє власника. Авторизований шлях використовує userLists і не має тієї самої доведеної помилки. ProfilesController анонімно перелічує всі профілі. Експлуатація на реальних приватних даних не виконувалася.
2. P1: клієнт онбордингу надсилає objects/scalar замість string[]/int[]; поточний AnswersRequest дійсно очікує primitive arrays. UI показує завершення й після помилки. Доведено зіставленням коду, не живою реєстрацією.
3. P1: головна відкидає всі seeds без TMDB ID. Відтворено в живому браузері.
4. P1: міграція бере списки через authenticated GET, який резолвить поточний акаунт, а не гостя. Часткові помилки ігноруються, глобальний guestMigrated записується без повного підтвердження. Це ризик пропущеної міграції/прихованого retry; видалення вихідних даних аудит НЕ довів.
5. P1: ID namespace неоднозначний: RunBySeedsAsync змішує internal ID і TMDB ID. Обидва поточні GET/POST використовують цей резолвер, тому твердження «POST завжди відхиляє internal ID» неправильне. Compatibility fallback на старіший API залишається проблемним, а поточний resolver потребує тесту колізії.
6. P1: бот передає TMDB ID у callback та seed-запити; каталог IMDb/anime/manga часто має tmdbId=null. ProfileId=1 також захардкоджений. Це доведено кодом; Telegram не тестувався.
7. P2: FR-8 filter parity бота не реалізовано в оглянутому клієнті/handler. Розширення винесено після блокерів.
8. P2: залишаються прогалини live auth/onboarding/migration, PWA offline/mobile, семантики, даних/збагачення, продуктивності та відтворюваного browser E2E. Наявний e2e/e4_accounts.py є API smoke, створює акаунти і не є браузерним E2E; на поточній БД його не запускали.

## Вебджерела

Під час вебаналізу додатково звірено PWA-вимоги з [Next.js PWA guide](https://nextjs.org/docs/app/guides/progressive-web-apps) та [MDN installability](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable). Manifest/SW/іконки самі по собі не доводять встановлюваність: потрібна перевірка підтримуваних браузерів і HTTPS або loopback. Ринкова/SEO-аналітика і статистика відвідувачів не виконувалися; цей аудит перевіряє працездатність вебпроєкту.
