# Технічне завдання — сервіс підбору фільмів, серіалів і телешоу

**Робоча назва:** TBD (пропозиції: «Кіногід», CineMatch, FilmFinder — фінальна назва не блокує розробку)
**Версія:** 1.0 (чернетка за результатами опитування замовника, 07.11.2026)
**Статус:** Е0-Е1, розширені фільтри, PWA, FR-12/13 (аніме/манга+імпорт), FR-14/15 (IMDb bulk 2.86 млн тайтлів без ключа + «Де подивитись»: sweet.tv/Internet Archive), FR-16/17/18 (акаунти, лайки/оцінки, профіль смаку, Кінотека-свайпи, онбординг) — виконано і верифіковано live (07.11.2026; E2E 16/16 + UI-флоу). Чекає від власника: TMDB_API_KEY (постери+TMDB-каталог+providers), MAL_CLIENT_ID (MAL-шар каталогу), Telegram-токен; Ollama (семантика)

## 1. Загальний опис

### 1.1. Призначення
Сервіс для пошуку фільмів, серіалів і телешоу за жанрами, характеристиками та пошуковим запитом, з головною фішкою — **підбором схожих тайтлів трьома способами**:

1. **Від картки** — «схоже на цей фільм» від будь-якого тайтла.
2. **За списком еталонів (multi-seed)** — користувач перелічує кілька фільмів/серіалів/телешоу («щось схоже на: The Office, Breaking Bad, ...»), система знаходить спільний перетин «настроєнь» і пропонує результати.
3. **Вільним текстом** — опис побажання своїми словами («щось легке, як ситком, але з детективним сюжетом»).

### 1.2. Форми існування
- **Веб-застосунок**, який спершу працює на домашньому сервері (локальна мережа), згодом — публічний сайт (домен, доступ ззовні). Єдина основа.
- **Мобільні застосунки (Android/iPhone)** — «ретранслятори» веба, без власної логіки: **PWA** (встановлення з браузера, іконка, повноекранний режим, офлайн-заглушка; покриває обидві платформи за $0) — реалізовано в Е0/Е1. Опційно пізніше: APK через Capacitor (прямое встановлення, без Play Store). Нативний iOS без платного Apple Developer ($99/рік) неможливий — свідомо за межами бюджету, PWA покриває iPhone.
- **Telegram-бот** — **повнофункціональний дублікат веба** (пошук, фільтри, усі режими схожості, списки).

### 1.3. Чим відрізняється від наявного
TMDB/IMDb дають лише фіксований «similar/recommended». Тут — керована схожість (multi-seed + фільтри + семантика з поясненням кожної рекомендації), українська локалізація, доступність на українських VOD-сервісах, особисті списки.

### 1.4. Цільова аудиторія (за етапами)
- Етап 1–2: власник, без акаунтів.
- Етап 3: сім'я/друзі — прості профілі без реєстрації.
- Етап 4: публічний сервіс з реєстрацією (закладено в архітектуру заздалегідь).

## 2. Межі проєкту

**У межах (in scope):** пошук, фільтрація, підбір схожих, картки тайтлів, трейлери/постери, списки користувача, провайдери перегляду, Telegram-бот, локалізація uk/en, скрапери відкритих метаданих, синхронізація переглянутого з Jellyfin/Plex/Trakt, спільні списки.

**Поза межами (out of scope):** відтворення/розміщення відеоконтенту, піратські джерела, рекомендаційна реклама, парсинг закритих API, додавання російськомовної локалізації.

## 3. Функціональні вимоги

### FR-1. Пошук і гнучкі фільтри
- Текстовий пошук: назва (uk/en), актор, режисер.
- Фільтри: **тип** (фільм / серіал / телешоу-токшоу), **жанри** (мультивибір), **рік/період**, **країна**, **мова оригіналу**, **рейтинг** (TMDB та/або IMDb, діапазон), **тривалість** (фільм: діапазон хв; серіал: тривалість серії), **кількість сезонів**, **статус** (завершений/онгоїнг).
- Сортування: релевантність, рейтинг, новизна, популярність. Пагінація / нескінченна лента.

### FR-2. Картка тайтла
- Постер, заставка (backdrop), короткий і повний опис, жанри, рік, країна, тривалість, режисер, ключові актори.
- Рейтинги: TMDB + IMDb.
- **Трейлер** — вбудований YouTube-плеєр (якщо є uk-трейлер — показати його, інакше en).
- Кнопки дій: «Схоже», «Хочу подивитись», «Переглянув(ла)» (+ опційна оцінка), «Де подивитись».

### FR-3. Схожість від картки
Блок «Схожі» (до 20 результатів) на кожній картці, **з поясненням** для кожного результату («спільні жанри: драма, кримінал; спільний актор X; близький тон опису»).

### FR-4. Схожість за списком еталонів (multi-seed)
- Користувач додає **1–10 тайтлів** через пошук-автокомпліт.
- Система агрегує схожість по всіх еталонах і повертає результати з поясненнями.
- Запит можна зберегти як «запит-добірку» й повторити/відредагувати пізніше.

### FR-5. Семантичний пошук текстом
- Вільний опис побажання → гібридний пошук (вектор запиту + розпізнані з тексту фільтри-сигнали).
- З результатів можна одразу перейти в режим «схоже на: [цей тайтл]».

### FR-6. «Де подивитись»
- Провайдери для регіону **UA** (стримінг / VOD-прокат / безкоштовно з рекламою) з прямими посиланнями.
- Джерела: TMDB watch providers (дані JustWatch) + власні скрапери українських сервісів (розділ 6).

### FR-7. Списки
- Системні списки: «Хочу подивитись», «Переглянуте» (+ опційна власна оцінка 1–10).
- Швидке додавання з картки і з результатів пошуку.
- Експорт списку (JSON/CSV) — nice to have.

### FR-8. Telegram-бот — повний паритет
- Пошук, фільтри, картка (постер, опис, посилання на трейлер), усі три режими схожості (в т.ч. multi-seed списком), списки.
- Ідентифікація профілю (на Е1 — єдиний локальний профіль, з Е2 — прив'язка до простого профілю).
- Бот споживає той самий backend API, що й веб (без окремої логіки).

### FR-9. Локалізація uk/en
- Інтерфейс з перемикачем uk ↔ en; всі системні тексти через i18n.
- Назви й описи тайтлів: українська де є в джерелі, fallback на англійську.

### FR-10. Облікові записи (еволюція)
- Е1: єдиний локальний профіль, без входу.
- Е2: прості профілі (ім'я + пін-код, без email-реєстрації) для сім'ї/друзів.
- Е4: повна реєстрація (email або OAuth). Модель даних з Е1 уже містить users/profiles.

### FR-11. Мобільний доступ (PWA «ретранслятор»)
- Веб є PWA: manifest (ім'я, іконки 192/512 + maskable, standalone, theme-color), service worker (кеш статики і постерів TMDB, network-first, офлайн-заглушка `/offline`), apple-touch-icon і мета-теги iOS.
- Встановлення: Android — Chrome/Edge «Додати на головний екран»; iOS — Safari «На екран „Домів“». Повноекранний режим без браузерного інтерфейсу.
- API GET не кешується SW (живі дані); POST не перехоплюється.
- Опційно (Е3+): нативний APK-обгортка через Capacitor для прямого поширення на Android.

### FR-12. Розділи «Аніме» та «Манга»
- Окремі розділи в навігації: **Аніме** (переглядається) і **Манга** (читається). Один unified-каталог у БД: `type='anime'` і `type='manga'` у titles.
- Джерела каталогу (безкоштовні, без ключів): **AniList** (GraphQL, 90 req/min) — PRIMARY каталог і назви (ромадзі/англ; uk-поле в AniList API недоступне); **MyAnimeList official API v2** (api.myanimelist.net, безкоштовний client ID з myanimelist.net/apis.php, env `MAL_CLIENT_ID`) — seasons + ranking (top anime/manga); **Shikimori** (shikimori.io) — імпорт списків/донор оцінок. **Jikan (api.jikan.moe) — EOL і недоступний з мережі власника**: клієнт лишається в коді (env `JIKAN_URL`, задіюється self-host/VPN), НЕ використовується для sync за замовчуванням. Російських назв Shikimori НЕ БУДЕ в uk-полях (тест покритий).
- Специфіка аніме в картці: формат (ТВ/Фільм/OVA/ONA/Спешиал), епізоди, студії, статус виходу; оцінки MAL/AniList/Shikimori окремими бейджами. Специфіка манги: томи, розділи, автори.
- Аніме/манга беруть участь у загальному пошуку (`type=anime|manga`) і в схожості (спільний движок по жанрах/keywords; семантика — як з'являться вектори).
- Списки: для аніме — звичайні «хочу подивитись/переглянуте»; для манги — список «Прочитане» (kind=`read`) з оцінкою 1–10.

### FR-13. Імпорт переглянутого/прочитаного з трекерів
- Джерела імпорту: **Shikimori** (anime_rates/manga_rates), **MyAnimeList** (через Jikan, публічні списки), **AniList** (GraphQL MediaListCollection публічних профілів). Без OAuth — користувач вводить нікнейм/ID публічного профілю; приватні списки → осмислена помилка.
- Що імпортується: статус `completed` (переглянуте аніме → «Переглянуте»; прочитана манга → «Прочитане») + оцінка користувача (шкали 1–10 трекерів мапляться напряму); опційно `watching/reading` → «Хочу подивитись».
- Матчинг: за зовнішніми ID (mal_id/anilist_id/shikimori_id); якщо тайтла нема в каталозі — створюється запис з метаданих імпорту (upsert, ідемпотентно).
- Імпорт — фонова джоба з прогресом (ліміти джерел: Jikan 3 req/s, AniList 90/min, Shikimori ~2 req/s; тротлінг обов'язковий), статус і статистика доступні опитуванням.

### FR-14. «Де подивитись»: провайдери перегляду
- Нова таблиця `watch_links`: title_id, provider (sweettv|archive|tmdb-streaming|...), kind (`free`|`subscription`|`rent`|`buy`), region (`UA`|`US`|`*`), url, is_available, checked_at. UNIQUE(title_id, provider, kind, region).
- **sweet.tv — PRIMARY UA-провайдер (парсинг)**: каталог `/ua-uk/movie` (патерн `/ua-uk/movie/{id}-{slug}`), картки фільмів дають назву укр., рік, маркери доступності (безкоштовно/передплата). Тротлінг і пошана robots.txt (NFR-6): каталог і картки дозволені; /search, /payment — заборонені і НЕ парсаться. uk-назви з sweet.tv пишуться в title_uk (це легальне джерело укр. назв).
- **Internet Archive — free-провайдер**: колекція `feature_films` (~28.6k повнометражок public domain) через advancedsearch API; матчинг до каталогу за нормалізованою назвою + рік (±1); знайдені → watch_links kind=free з прямим посиланням.
- **TMDB watch/providers — dormant до ключа**: env `TMDB_API_KEY`; коли з'явиться — провайдери JustWatch (регіон UA) через `find/{imdb_id}?external_source=imdb_id` → `/watch/providers`. Без ключа — чесний 400/пропуск, нічого не ламається. Прямий скрапінг justwatch.com НЕ РОБИМО (ToS забороняє; санкціонований канал — TMDB).
- UI: на картці та сторінці тайтла блок «Де подивитись» з бейджами провайдерів (free/передплата) і посиланнями; фільтр пошуку «лише те, що можна подивитись» (exists watch_links available).

### FR-15. Масивний каталог фільмів/серіалів (IMDb datasets, без ключа)
- Джерело: офіційні IMDb datasets (datasets.imdbws.com, доступні без реєстрації, умова — атрибуція IMDb у README/футері): `title.basics.tsv.gz` (~10 млн тайтлів) + `title.ratings.tsv.gz`. `title.akas.tsv.gz` на Е2 не тягнемо (занадто великий; uk-назви — з sweet.tv і пізніше TMDB).
- Мапінг titleType: movie, tvMovie, video, tvSpecial, short → `type='movie'`; tvSeries, tvMiniSeries → `type='series'`; tvEpisode і videoGames — SKIP. Поля: primaryTitle/originalTitle, startYear, runtimeMinutes, genres (canonical lowercase), isAdult, averageRating→rating_imdb, numVotes→popularity (лог-нормалізація як для інших джерел).
- Реалізація: потокове завантаження .gz у контейнері, PG COPY у staging-таблицю imdb_raw, MERGE-злиття в titles за imdb_id (idempotent); повторний запуск оновлює, не дублює. Стейджинг чиститься після злиття.
- Пошук `type=movie|series` працює з масивним каталогом; сортування за популярністю (numVotes) — реальні IMDb-топи.

### FR-16. Акаунти, реєстрація, захист
- ASP.NET Core Identity (EF store): email + username + пароль (вбудоване хешування). Політика пароля: ≥8 символів, цифра + велика літера. Lockout: 5 невдалих спроб → 15 хв. Реєстрація/логін — rate-limit (login 5/хв/IP, register 3/год/IP, вбудований .NET RateLimiter).
- Cookie-автентифікація (HttpOnly, SameSite=Lax; Secure — на публічній стадії Е4+). Ендпоінти: `POST /api/auth/register`, `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/me`. Помилки логіна генеричні («невірний email або пароль») — без розкриття існування акаунта.
- Авторизація: списки/оцінки/discover — лише для свого профілю. Анонімний гостьовий режим лишається (як зараз), але з акаунтом дані персистентні. Email-підтвердження НЕ блокує (SMTP ще не підключений; поле залишено на майбутнє).
- Голосування/дії записуються з user id; німе логування спроб логіну (без паролів).

### FR-17. Лайки/дизлайки, оцінки, пам'ять про користувача
- `list_items` розширюється kind: `liked` | `disliked` (поряд з watchlist/watched/read); оцінка 1–10 на watched (масштаб, узгоджений з трекерами). UNIQUE(profile,kind,title) — ідемпотентно.
- Таблиця `user_profiles`: user_id FK, taste_genres jsonb (жанр→вага), taste_keywords jsonb, taste_era jsonb (декада→вага), taste_actors jsonb, negative_genres jsonb (жанр→cooldown-вага), onboarding_done bool, quiz jsonb, updated_at.
- Таблиця `interaction_log`: user_id, title_id, action (like|dislike|rate|watchlist|watched|skip|open), value (оцінка), created_at — повна історія взаємодій («пам'ять про користувача»); профіль агрегується з неї, ніколи не втрачається.
- Перерахунок профілю інкрементально після кожної дії: like +1.0; оцінка (r−5.5)/4.5×1.2; watchlist +0.4; dislike −0.8 (і +cooldown негативному жанру); часовий спад внесків (напівжиття 60 днів). Сигнали: жанри, keywords, ера (декада), актори; семантичні вектори — додадуться, коли з'явиться Ollama (ваги в SimilarityOptions-стилі конфігу).

### FR-18. Режим «Кінотека-свайпи» (discover) + онбординг
- `GET /api/discover?count=10` (авторизований): кандидати з titles, яких нема в liked/disliked/watched/watchlist; скоринг за user_profiles (жанри+era+актори+rating+popularity; семантика пізніше). Diversity: ≤2 тайтлів одного жанру в одній видачі; 70% exploitation (найкращий прогноз) / 20% safe (популярні високооцінені близькі до профілю) / 10% exploration (жанр з онбординг-цікавостей, яких мало в профілі).
- Anti-fatigue (за рішенням власника: БЕЗ обмежень на дизлайки): дизлайк лише знижує вагу профілю (−0.8 + cooldown негативного жанру в negative_genres); streak-лічильників і пауз НЕМАЄ. Окрема дія «Not now» (skip) — не впливає на профіль зовсім.
- `POST /api/discover/action {titleId, action: like|dislike|skip|watchlist|watched}` → пише в list_items + interaction_log, інкрементально оновлює профіль.
- Онбординг після реєстрації: 8–12 мультивибірів по постерах (жанри/настрій/ера) + 3 улюблених тайтли через пошук → cold-start профіль. `POST /api/onboarding/answers`. Квіз можна пропустити (onboarding_done=false не блокує нічого, але discover до квізу працює лише на popularity+safe).

## 4. Нефункціональні вимоги

| № | Вимога |
|---|--------|
| NFR-1 | Пошук/схожість по локальному індексу: ≤ 1 c (p95) без звернення до зовнішніх API. |
| NFR-2 | Локальний індекс: ≥ 50 000 найпопулярніших тайтлів (фільми+серіали) з описами та векторами. |
| NFR-3 | Усі зовнішні виклики кешуються в БД; повторний запит не б'є у зовнішній API. Метадані тайтла — фактично безстроковий кеш з інвалідацією при оновленні. |
| NFR-4 | Деградація без аварії: якщо зовнішній API недоступний — працюємо з кешем, показуємо попередження. Ретраї з backoff, черга синхронізації. |
| NFR-5 | Ліміти: TMDB ~50 req/s; OMDb free — 1000 запитів/день (пріоритет популярним тайтлам, решта — on-demand). |
| NFR-6 | Скрапери: rate ≤ 1 req/2 c на хост, пошана robots.txt, randomisiований UA, кеш результатів. |
| NFR-7 | Приватність: дані користувачів лише локально до Е4; жодної зовнішньої аналітики. |
| NFR-8 | Атрибуція: логотип/текст TMDB у футері (обов'язкова умова API), атрибуція JustWatch для провайдерів. |
| NFR-9 | Розгортання: Docker Compose на Ubuntu homelab; оновлення без втрати даних; автоматичні бекапи БД (щоденні). |

## 5. Архітектура і стек (рішення)

| Компонент | Вибір | Обґрунтування |
|---|---|---|
| Backend | **ASP.NET Core 8 (C#)** | Стек користувача; performance-критичне ядро нативно; веб і бот споживають один REST API |
| Frontend | **Next.js (React) + Tailwind** | Перевірений патерн власника (solar.is); SSR/ISR; постери з CDN TMDB |
| БД | **PostgreSQL 16 + pgvector** | Реляційні дані + векторний пошук в одній БД; EF Core |
| Embeddings | **Ollama, модель bge-m3 (1024 dim, uk/en)** | Локально й безкоштовно; багатомовність критична (uk-описи + en-fallback + uk-запити); існуючий сервіс у господарстві |
| Векторний пошук | pgvector (HNSW); MVP-альтернатива — in-memory SIMD (System.Numerics.Tensors) | 50k × 1024 float32 ≈ 200 МБ RAM — тривіально для homelab |
| Telegram-бот | **Telegram.Bot (C#)**, long polling (Е1–3) → webhook (Е4) | Той самий стек, той самий API |
| Фонові задачі | BackgroundService / періодичні джоби в api | Обсяг невеликий, окремий worker не потрібен |
| Скрапери | Окремі конектори в backend, інтерфейс `IContentSource` + rate-limiter | Модульність: легко додати/відключити джерело |

**Схема:**

```
Користувачі (браузер, Telegram)
        │
   ┌────┴─────┐
   │ Next.js  │      Telegram-бот (C#)
   └────┬─────┘            │
        └──────► ASP.NET Core API ◄──────┘
                   │      │      │
        ┌──────────┘      │      └───────────┐
   PostgreSQL+pgvector  Ollama      TMDB / OMDb / Wikidata
   (каталог, вектори,   (embeddings) (клієнти з кешем)
    списки, кеш)                │
                        Скрапери: Кінопошук, UA VOD (Megogo,
                        Sweet.tv, 1+1 video), YouTube-трейлери
```

## 6. Джерела даних

| Джерело | Що дає | Ліміти / примітки |
|---|---|---|
| **TMDB API** (ядро) | Каталог, метадані, uk-локалізація, жанри, keywords, credits, similar/recommended, watch providers (UA), трейлери, постери | ~50 req/s; реєстрація безкоштовна; обов'язкова атрибуція; щоденні export-дампи ID для повноти каталогу |
| **OMDb API** | IMDb rating, Metascore, нагороди | Free: 1000/день → кешувати; ключ on-demand |
| **Wikidata** | Ідентифікатори й зв'язки (особливо для телешоу) | Спорадично, без лімітів |
| **Скрапер: Кінопошук** | Рейтинг/відгуки, яких немає в TMDB | Ризик антибот-заходів; альтернатива — неофіційний kinopoisk.dev API; низький rate |
| **Скрапер: UA VOD** (Megogo, Sweet.tv, 1+1 video, Kyivstar TV) | Доступність тайтлів в Україні (такі сервіси погано покриті JustWatch) | Скрапінг публічних сторінок каталогу; пріоритетний порядок — уточнити (відкрите питання 13.2) |
| **YouTube** | Офіційні трейлери, відсутні в TMDB | Пошук «{title} {year} official trailer», кеш посилань |

**Стратегія синхронізації:**
1. Первинний імпорт: топ-50–100k тайтлів (фільми + серіали) через TMDB discover/export — батчами вночі.
2. Щоденний інкремент: новинки + оновлення популярних.
3. On-demand для «хвоста»: перший запит тягне з API, зберігає в кеш назавжди.
4. Вектори перераховуються батчами при оновленні опису тайтла.

## 7. Модель схожості (ядро проєкту)

### 7.1. Сигнали та початкові ваги (налаштовуються в конфізі)

| Сигнал | Вага | Як рахується |
|---|---|---|
| Семантична близькість описів | 0.35 | cosine(bge-m3 vector) |
| Спільні ключові слова TMDB | 0.20 | overlap keywords |
| Жанри | 0.15 | Жаккар |
| Спільні актори / режисер | 0.15 | overlap credits (режисер ×2) |
| Епоха | 0.05 | рік ±7 років — 1, далі спад |
| Близькість рейтингу/тривалості | 0.05 | гауссова близькість |
| TMDB similar/recommended | 0.05 | слабкий сигнал-буст |
| Бонус «тип» | ×1.1 | фільм↔фільм, серіал↔серіал |

### 7.2. Multi-seed (список еталонів)
- Вектор еталона: **середнє векторів** усіх seed-тайтлів.
- Метадані: об'єднання жанрів/акторів/keywords з вагою за кількістю seed-тайтлів, де зустрічається ознака.
- Кожен результат супроводжується **топ-3 причинами** («жанр: трилер у 2 з 3 еталонів; спільний актор; близький тон»).

### 7.3. Вільний текст
- Embedding запиту через ту саму модель + легкий keyword-extraction з тексту (жанри, настрій) як soft-фільтри.
- Гібридний score: vector similarity × фільтри-бонуси.

### 7.4. Якість і калібрування
Golden-set перевірок (фіксується в тестах): напр. «The Office → ситкоми з імпровізацією, не драм-трилі», «Fight Club → твістер-психологія, не бойовики». Проходження golden-set — частина приймання Е2.
Майбутнє (Е3+): колаборативні сигнали з переглянутого/оцінок профілів.

## 8. Модель даних (стисло)

- `titles` — tmdb_id, type, title_uk/en, overview_uk/en, year, country, genres[], keywords[], actors[], director, runtime, seasons, rating_tmdb, rating_imdb, poster_url, backdrop_url, trailer_yt_id
- `providers` — title_id, provider, kind (stream/rent/buy/free), url, source (justwatch/megogo/...)
- `users` / `profiles` — від Е1 (єдиний) до Е4 (реєстрація)
- `lists` — user_id, kind (watchlist/watched), title_id, rating (nullable), created_at
- `queries` — збережені multi-seed запити
- `embeddings` — title_id, model, vec vector(1024)
- `source_cache` — source, key, payload jsonb, fetched_at, ttl

## 11. Етапи та критерії приймання

**Е0 — Каркас:** Docker Compose підіймається, всі сервіси здорові; TMDB-клієнт з кешем; схема БД; CI-скелет.
✅ `docker compose up` на homelab підіймає web+api+db; тестовий запит до TMDB кешується в БД.

**Е1 — MVP (веб, локально):** каталог, фільтри, картка (трейлер/постер/опис/рейтинги/провайдери UA), «схоже» від картки, списки.
✅ Приймання:
1. Пошук «Друзі» знаходить серіал < 1 c.
2. Фільтри (жанр+рік+рейтинг) працюють **по локальному індексу без зовнішніх викликів** (перевіряється логом).
3. Картка показує трейлер, постер, український опис (де є), провайдерів UA.
4. «Схоже» від картки: 20 результатів, кожен з поясненням.
5. Списки зберігаються в БД і переживають рестарт контейнерів.

**Е2 — Семантика + multi-seed + бот:** вільний текст, списки еталонів, Telegram-бот з паритетом, перемикач uk/en.
✅ Golden-set схожості проходить; у боті `/similar The Office, Breaking Bad` повертає добірку; uk/en перемикання не ламає дані.

**Е3 — Скрапери + трекери:** Кінопошук-рейтинг на картці; доступність Megogo/Sweet.tv/1+1; синхронізація переглянутого з Jellyfin/Plex/Trakt.
✅ Картка популярного фільму показує рейтинг Кінопошуку і ≥ 1 UA-провайдера зі скрапера; переглянуте з Jellyfin потрапляє в список.

**Е4 — Профілі + публічність:** прості профілі (Е2) → реєстрація, спільні списки, публічний домен + HTTPS + webhook бота.
✅ Два профілі бачать спільний список; реєстрація працює; бот через webhook; сайт доступний ззовні.

## 12. Ризики та заходи

| Ризик | Заходи |
|---|---|
| Кінопошук блокує скрапінг | Низький rate, кеш; fallback на kinopoisk.dev; нарешті — просто прибрати джерело (не критичне) |
| Uk-описи в TMDB неповні | Fallback en; (опційно, Е2+) локальний переказ через Ollama з позначкою «машинний переклад» |
| OMDb 1000/день | Пріоритет популярним; on-demand для решти; кеш назавжди |
| Атрибуція JustWatch/TMDB | Виводити обов'язкові атрибуції у футері та на картках |
| Telegram webhook потребує HTTPS | До Е4 — long polling, публічність відкладена |
| Телешоу/ток-шоу мають слабкі метадані в TMDB | Сигнали схожості для них зважуються інакше (keywords+семантика важче); Wikidata-донор |
| Скрапінг і ToS | Тільки публічні метадані, robots.txt, кеш, ідентифікація «educational/personal» на Е1–3; перед публічним запуском переглянути юридичний статус |

## 13. Відкриті питання (не блокують Е0–Е1)
